# Approved supplier products in the public catalogue

Status: Development **Implemented** for the listing, search, category, detail, supplier-profile and inquiry links; QA **Not Started / BLOCKED** (no isolated database: `it-approved-flow.mjs` is prepared, not run). Nothing deployed, no production data touched, no migration run.

## Trace (audit result) and the links that were missing
Draft -> submitted revision -> admin approval (`publication.snapshot`) was built. Missing: any public reader of it; a public supplier identity for a company without a seeded seller; a way to address an inquiry to such a company; price-on-request display; category counts that include approved products; separation of category management from public discoverability. All are now connected. NOT done (see Blockers): homepage sections, saved-products views, related products, an unpublish/archive action, a persisted unified catalogue.

## Architecture (one engine, no second catalogue)
- **Source of truth for public content:** `supplier_products.publication.snapshot` only. `src/lib/catalog/approvedProducts.ts` loads it into an in-memory snapshot (`approvedStore.ts`). The query projects only `slug, companyId, archivedAt, publication`: drafts, pending/rejected revisions, review notes and documents are never read. A pending edit therefore never replaces the live approved content.
- **One eligibility rule** (`isEligibleDoc`): `publication.state === "APPROVED"` AND not `archivedAt` AND the category exists and is active (management list) AND the owning `supplier_companies` row is `ACTIVE`. No verification or paid plan is required or implied.
- **CSV + MongoDB, one engine:** the existing listing engine (`categoryListing.ts`) gets approved products as a third row source (`kind: "approved"`) merged into the same in-memory indexes (All Products, search, every category, subcategory, a company's own list). Filtering, facets, sorting, totals and pagination are therefore computed once over ONE row set: no per-request fetch-concatenate-slice, counts are exact for the snapshot, ordering is deterministic (source order, then approved by id), tie-breaker is the row position. Indexes are rebuilt only when the snapshot version changes. Bound: at most `MAX_APPROVED = 2000` approved products (operational cap, reported by the loader).
- **Identity:** product `sp-<productId>` (cannot be all digits, never shadows a catalogue or sample URL: catalogue and sample resolve first, then approved by slug). Supplier: public slug `c-<companyId>`, inquiry key `co:<companyId>`. The key is added to the session context of the company in memory only (never stored in `sellerKeys`, which stays admin-linked catalogue sellers), so every existing `supplierKey in company.sellerKeys` scope (inbox, responses, quotations, orders, notices) already covers it and a new supplier never claims a seeded seller. Duplicate ids/slugs in the snapshot are dropped (first wins).
- **Categories:** public discoverability = active AND has eligible products (counts now include approved products at every path level); `getManagementCategories()` lists every category for supplier product creation and approval, so an empty category is never hidden from management. Note: the repository has no stored admin activation flag (`isActive` is true for every curated category).
- **Price model:** FIXED or ON_REQUEST (the only modes the product form has; no range/tier data exists). ON_REQUEST has no price number anywhere (`price.min = null` in the public DTO), never matches a price filter and sorts after every priced product. INR only; units are the supplier's own stated unit and are never converted or compared.

## Public surfaces connected
All Products, search, category and subcategory pages, supplier product lists (`/suppliers/c-.../products`), product detail (`/products/<slug>`), company profile (`/suppliers/c-...`), public product/supplier APIs, the inquiry form's product list, category directory counts. Not connected: homepage sections, saved products/wishlist/compare views of an `sp-` product, related products on a supplier product, reviews (none exist).

## Inquiry flow
Buy button -> existing form -> `POST /api/public/inquiries` (unchanged pipeline): supplier from `c-` slug via `getPublicSupplierBySlug`, product by id, `found.supplier.slug === supplier.slug` is enforced server-side (a forged product/supplier pair is refused), eligibility is the snapshot's, then the central `submitInquiry`. The inquiry is addressed to `co:<companyId>` (DIRECT, original). Automatic matching: `buildJob` only builds a job for numeric catalogue product keys, so supplier products are not matched and the central distribution code was not touched or duplicated; extending matching to them needs a product-equivalence design (see `docs/leads/MATCHING_POLICY.md`).

## Public DTO and API
Allow-listed (`toPublicProduct`, `ProductDetail`, `SupplierDetail`): id, slug, name, url, image, price (min null for on request), moq, category, supplier {id, name, slug, url, city, verificationStatus: always "unverified"}, `source: "supplier"`. Never: company id on the product DTO, draft or review data, SKU, contacts, documents. List endpoints keep the existing bounds (default 20, max 50, validated sort/filter allow-lists in `listingQuery.ts`).

## Images
One normaliser (`normalizeImage`): string/array/nested url, https from an allowed host (`assets.myntassets.com`, `www.finbynkart.com`, `ik.imagekit.io`; next/image is configured for the same hosts) or a site-relative path; anything else is dropped (no blob URLs, no random fallback). Cover = first image in the approved snapshot, gallery order preserved: the same `images[0].src` feeds the card, listing, search, category, detail and supplier profile. Missing image: the existing neutral tile.

## Cache and freshness
Snapshot TTL `FINBYN_APPROVED_CACHE_MS` (default 60 s). An approval calls `invalidateApproved()` after its transaction commits (this process sees it at once). Other instances converge within the TTL; a stale snapshot starts a non-blocking refresh and pages/APIs `ensureApproved()` on first use. A failed load keeps the previous snapshot, is retried by the next reader and requests are not held up again for 15 s. Honest limits: on a multi-instance deployment a change can take up to one TTL to appear; the listing result cache (`FINBYN_LISTING_CACHE_MS`) is keyed by the index identity so it follows snapshot changes. There is no unpublish action yet: `archivedAt` is respected if set, but nothing sets it.

## Migration
None needed (no schema change; no new collection; no new index: `published_by_category` already serves the loader query). No unified persisted catalogue exists to reuse. If the catalogue later moves to MongoDB, import the CSV as a source and keep these id namespaces.

## Blockers and decisions
Runtime and E2E of the whole chain (create draft, review, approve, find, inquire) are unverified; responsive/accessibility runs of the changed pages with real approved data were not done; no `explain` or latency numbers; homepage sections, saved-product views, related products, an unpublish action and matching for supplier products are not built; the 2,000-product snapshot cap and 60 s TTL are product decisions to confirm; when the database is down the first request per 15 s waits for the connection attempt before serving catalogue-only content.
