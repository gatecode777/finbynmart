## Scope and boundaries
This is a platform review of **business evidence** submitted for a company. It is not government or registry verification, product-quality certification, e-mail or phone confirmation, profile completeness, Active/Suspended status, product moderation, seller ownership or payment status; none feeds in or out of it. Approval does not activate a suspended company, publish a product or move seller ownership (tested in `it-admin-verification.mjs`, BLOCKED).

## Implementation map (audit)
- **Reused:** the company (`supplier_companies`, its existing `verificationStatus` field, previously always UNVERIFIED), the uploaded evidence (`company_documents`, validated by size, extension and magic bytes, stored privately by `src/lib/buyer/documentStorage.ts`), the supplier Company page tabs (KYC Documents, Verification), the admin shell, guards, `adminAuditLog`, `notifySupplier`, `invalidateApproved`, the worker sweep, the Page 52/57 drawer, tab and dialog components.
- **Found and fixed on the supplier page:** the Verification tab claimed a static "Official Trust Seal: In Review", "higher ranking in buyer search", "direct requests from enterprise buyers" and a badge on all listings (none true), and called an upload "Submitted". Those claims are removed; an upload is "Uploaded".
- **Policy source:** none existed. The convention is configuration (the `QUOTATION_TAX_RULES` pattern): `VERIFICATION_POLICY` (JSON), documented in `docs/config/VERIFICATION_POLICY.md`, no default. Missing or invalid = submission and approval blocked with an actionable message.
- **Storage limit (existing):** evidence lives in the local private directory `BUYER_DOCS_DIR`; production has no hosted private store yet (uploads are refused there). Documents are not malware-scanned and none is claimed to be.

## Data model (additions only)
`verification_submissions` (one document per **submission revision**): reference `VER-YYYY-XXXXXX`, `companyId`, `revision`, `latest`, `state` (PENDING_REVIEW, CHANGES_REQUESTED, APPROVED, REJECTED, SUPERSEDED), record `rev`, a **copy of the policy**, the **identity snapshot**, the **evidence** (document id, stored file, size, SHA-256), submitter and time, idempotency key, and the decision (reviewer, time, reason code and label, the supplier-visible message, internal note, the reviewer's checklist, policy version). Indexes: unique reference; unique `{companyId, revision}`; unique one-PENDING_REVIEW-per-company (partial); unique `{companyId, idempotencyKey}` (partial); the queue `{state, submittedAt, _id}` and `{submittedAt, _id}` (partial on `latest`); `{evidence.documentId}`. `verification_events` (unique `dedupeKey`): the durable intent of each supplier notice and public refresh. `supplier_companies.verification` (written only by the approve decision): submission, reference, revision, policy version, time, reviewer, the approved identity, the material fields and the expiry the policy defined. **No migration, no backfill, no production write.** Counts: awaiting review = applications (at most one per company); changes requested, rejected = companies whose latest submission is in that state; approved = companies with a stored approval (a revision is never another company).

## Flows
**Supplier:** `GET/POST /api/supplier/company/verification` (company from the session; GET creates nothing). Submit snapshots the identity and the exact evidence, reads each stored file once to record its hash, refuses missing required evidence, a policy that does not apply, an unreadable file, an identical pending submission, and a resubmission the policy forbids; a waiting submission is superseded in the same transaction; a retry with the same key answers the stored submission. **Reviewer:** `GET /api/admin/verification` (queue), `…/[reference]` (submitted snapshot, current-profile differences, policy checklist), `…/history`, `POST …/approve | request-changes | reject`, `GET …/documents/[id]`. Statuses 401, 403, 404, 409, 413, 422, 429, 503 safe.
**Decision:** one snapshot transaction: conditional update on `{state: PENDING_REVIEW, rev}`, for an approval the company's stored approval, the audit row (unique `operationKey`, request hash) and the event. The checklist is the reviewer's own confirmation validated against the submission's policy copy; approval needs every criterion, a valid policy, complete required evidence and **every evidence file re-read (present, same size, same SHA-256) before committing**. A reviewer cannot decide a submission they made or a company they own. Same key + same decision = original answer; same key + different decision = 409; stale `rev` = 409. Request-changes and reject never alter an earlier approval and delete nothing. No revoke control exists (no approved workflow).

## Capabilities (default deny)
`verification.read`, `.documents` (private evidence), `.notes` (record and read internal notes; `.audit` can read them too), `.requestChanges`, `.reject`, `.approve`, `.audit` (audit events including evidence access). Every route needs `verification.read`. Scope = capability (no organisation, category or region scope exists).

## Private evidence
Served only through the authenticated admin route, re-authorized every request, as a non-inline `no-store` attachment (`nosniff`, sandbox CSP). The file must belong to that submission and still match the recorded hash (a changed file is not served). **Each opening is audited before any byte is returned; if the audit row cannot be written the file is not served.** No signed or long-lived link exists, so there is nothing issued to revoke. The file never enters public DTOs, search or caches. A supplier removing a document a submission relies on keeps the stored file.

## Public label and effective status
The public label ("Reviewed by Finbyn Mart", a platform review, never government or quality certification) needs the **effective** rule: a stored approval AND the policy's material identity fields unchanged since approval AND the approval not past the expiry the policy defined at approval time (none = never). An identity change withholds the label without deleting the approval; a later pending, changes-requested or rejected submission does not remove an existing approval. Wired into the approved-product loader (`ApprovedSupplier.verified`) and so into the listing, product and supplier DTOs for company-owned suppliers; the supplier Verification tab and the admin Supplier Management detail show the same effective status. Legacy catalogue sellers remain unverified (no data). Cache: approval triggers `invalidateApproved()` after the commit; a failure leaves the event pending and the worker sweep (`runDistribution` → `sweepVerificationEvents`) retries; stale display is bounded by the snapshot TTL (60 s) per instance.
