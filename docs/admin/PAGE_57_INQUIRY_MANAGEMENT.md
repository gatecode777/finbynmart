## Facts kept apart
Requirement lifecycle (stored inquiry status, grouped) · source (`DIRECT_INQUIRY`, absent = direct, or `GENERAL_REQUIREMENT`) · distribution job state (`PENDING, PROCESSING, COMPLETED, NO_MATCHES, PARTIAL, FAILED, STOPPED, PAUSED`) · recipient progress (each recipient's own) · quotation lifecycle (its own). **"Needs attention" is a UI grouping only** of two real conditions: a FAILED job, or a PARTIAL job that recorded an error. `NO_MATCHES` is a successful finished search and never attention.
DIRECT access lives on the inquiry (`supplierKey`); the admin DTO presents it as a recipient row (`kind: DIRECT`) and **never writes a duplicate recipient document**. A general requirement has no selected supplier even if its reference product has a seller.

## Capabilities (default deny, from the account record on every request)
`inquiries.read` list, counts, summary detail · `inquiries.requirements` requirement content (specifications, message, delivery, required-by) · `inquiries.recipients` recipient view · `inquiries.responses` (existing) supplier responses and quotation summaries · `inquiries.routing` routing repair and retry · `inquiries.distribution` pause and resume · `inquiries.audit` administrative activity · `inquiries.export` (existing). Every route also needs `inquiries.read`. No capability exposes buyer or supplier e-mail, phone or address (none is returned by any admin DTO). **Scope = capability only:** the admin model has no organisation or category scope, so none is implied. **Migration note:** an admin who held only `inquiries.read` used to see message and delivery text; that now needs `inquiries.requirements`. An operator grants it in the database (`ADMIN_ACCESS.md`).
Not built and not offered: moderation (no approved policy defines hiding or restricting an inquiry: the button is disabled and states the blocker); impersonation; deleting recipients; reassignment; manual broadcast.

## API
`GET /api/admin/inquiries` (q, source, group, dist, start, end, page, limit; unknown enum or bad date = 422; default 20, max 50, `createdAt,_id` tie-break; counts in the same response, so no separate summary endpoint) · `GET …/[reference]` · `GET …/[reference]/recipients` · `GET …/[reference]/activity?cursor=` · `POST …/[reference]/routing {companyId, reason, idempotencyKey}` · `POST …/[reference]/distribution {action: pause|resume|retry, reason, expectedRev, idempotencyKey}` · `POST /api/admin/inquiries/export`. Statuses: 401, 403, 404 (unknown or malformed reference, identical), 409, 413, 422, 429, 503 safe. Responses are `private, no-store`.

## Routing repair policy
Allowed only when: the requirement is open; the job is COMPLETED, PARTIAL or FAILED (not running, paused, NO_MATCHES or STOPPED); the company is a **frozen candidate** of the job (the matching cutoff) with no recipient row, is not the selected supplier's company, and **satisfies the matching policy now** (`freeze(job)` recomputed on the server). A company that matches now but was outside the cutoff is only **counted** ("outside the matching cutoff"), never added. The commit runs the worker's own routine (`addRecipientIn`) in one transaction with the audit row, which rechecks the inquiry (open), the company (ACTIVE, owns the seller) and the product (still public), refuses a duplicate (unique inquiry + company index) and records `origin: ADMIN_ROUTING`. One in-app lead notice follows the commit through the existing `deliverNotice` (subject to the supplier's alert preference; a failure leaves it queued for the worker sweep).

## Pause, resume, retry
Pause (job PENDING, PROCESSING or PARTIAL): sets `PAUSED`, `pause{at,by,reason,previousState}`, increments `adminRev`, **drops the lease**. **Concurrency guarantee:** every worker recipient commit first writes the job document (`touchedAt`) inside its transaction, conditional on `state: PROCESSING` and its own lease; a pause is a write to the same document, so either the recipient commits before the pause committed, or the transaction conflicts, retries, sees `PAUSED` and the worker abandons the job without writing a state. Writes the worker made after loading its job are no-ops (their filter carries the dropped lease). Existing recipients, conversations and quotations are untouched and the inquiry is not closed. Resume (PAUSED, requirement open): back to PENDING (or PARTIAL when candidates are frozen) from the saved cursor; duplicates are impossible (unique index). Retry (FAILED, or PARTIAL with a recorded error; requirement open): `attempts` reset, same frozen list and cursor, `lastError` cleared; a completed job is never re-run and no job is recreated or re-matched under a new policy. Pause, resume and retry are conditional on `{state, adminRev}`; a stale view is 409.
The buyer sees a paused job as "On hold: not processing right now" (never "cancelled", never a choice).

## Audit, idempotency, outbox
Each change inserts its `admin_audit_log` row **in the same transaction**: actor (session), action, `inquiryReference`, ids, safe reason (10–500 characters, internal), before/after state, server time, unique `operationKey` (`admin:action:idempotencyKey`) and a request hash. A retry finds the row and returns the original answer (`replay: true`); the same key with a different request is 409; a concurrent identical request is caught by the unique index. The audit row is mandatory: if it cannot be written the transaction aborts and the API answers 503 with nothing changed. The lead notice is the recipient row's existing durable notice state (the outbox for this flow). Exports write an `INQUIRIES_EXPORTED` row (counts and filter names only). The Activity tab shows this log (cursor-paged, 20 per page) and is separate from the buyer-visible lifecycle history.

## Data and indexes
New fields (optional, absent on old documents, no migration or backfill): `distribution_jobs.adminRev`, `.pause`, `.touchedAt`; `inquiry_recipients.origin`. New indexes (created lazily, idempotent): `inquiries {sourceType, createdAt, _id}` (`admin_inquiries_source`), `admin_audit_log` unique partial `operationKey` and `{inquiryReference, at, _id}`. Search is a reference prefix (unique index) or an anchored, escaped product-name prefix bounded by the date range (a scan of the range, stated on the page). The distribution filter and the "needs attention" count join the job (unique `inquiryId` index) after the inquiry index narrows by date; **`explain` was not run** (no isolated database), so their cost on a large collection is unmeasured.

## Sign-in return
Done with the earlier layout fix: anonymous visitors reach `/sign-in?next=<page path + validated filter state + open review>`; `safeNext` validates it (same-site path, no `//`, no backslash, no scheme, no `/api/`), the server resolves the landing path from the stored role, and a wrong-role user goes to their own portal home. Direct review links use `?review=FBM-INQ-…`.
