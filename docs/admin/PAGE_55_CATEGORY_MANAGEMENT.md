# Admin Category Management (original tracker Page 55, `/admin/categories`)

Status 2026-11-16: **Design: not marked complete. Prompt: delivered. Development: PARTLY implemented: hierarchy browse, search and filters, effective-status and impact review, audited activation of MAIN categories enforced across the platform, and administrative activity. NOT implemented: create category, rename or re-describe, change parent, change slug, activation below a main category (each blocked for a stated reason).** QA: In Progress (unit and real-taxonomy checks ran; every database and authenticated-browser check is BLOCKED). Not Functionally Verified.

## Audit result (what the taxonomy really is)
Categories are **not database records**. They are code: the ten curated main categories (`constants/categories.ts`, with their sample listings in `categoryPages.ts` and their approved images) and, for apparel only, departments and product categories derived from the catalogue CSV files. A synchronous in-memory directory (`getCategoryDirectory`) builds `nodes` (publicly discoverable), `management` (all nodes, for supplier selectors) and counts; `isActive` was hard-coded `true`. Three levels exist (main → department → product category), ids are slug paths, and public URLs, product references, approved snapshots, the supplier forms and the attribute and matching definitions are all keyed to those ids and slugs. There is no redirect or alias layer. The listing engine keys departments and product categories by catalogue names, not by node id.

## What was built
- **One central activation overlay.** `category_overrides` (`_id` = main category id, `isActive`, `rev`, internal `reason`) is written only by the activation change and read by the one directory, so there is a single effective model: `effectiveActive(node)` = its main category is not deactivated (every node below follows it); `discoverable` = effectiveActive AND eligible public products (or an eligible child). The overlay lives in the same in-memory store as the approved snapshot (`approvedStore.ts`); it is loaded **before** the approved snapshot on every refresh, a failed read keeps the **last known set** (a deactivation is never lost to a refresh failure), the directory cache and the listing indexes are keyed on the snapshot **and** overlay versions.
- **Enforcement** (all central, no page-specific lists): navigation, category pages and the category URL (unavailable = the established not-found), All Products, search, the industry listing and supplier public product lists (via the directory and the engine's base index), supplier product selectors (`getManagementCategories`), the approved-product loader (a product of an inactive category leaves the public snapshot), product detail pages and the product reference used for a new inquiry (catalogue, sample and supplier products), and the authorization-grade checks that read the **database**: `isProductPublicNow` (new inquiries, lead commits) and the worker's catalogue-lead commit now require the category to be active (`categoryActiveNow`).
- **Admin page** `/admin/categories`: hierarchy panel with lazy child loading (disclosure buttons with `aria-expanded`, not a tree widget), search (name or slug prefix), level and status filters, paginated table (desktop) and cards (mobile), drawer with details, path, effective status, public visibility, eligible products **with the scope of the count stated** (a main category counts its whole branch, other levels their own level, always **without the activation gate**, so an inactive category can show products while hidden), the impact summary, activity, and the activation dialog (consequences, required reason). Add Category and the edit fields are disabled with the specific blocker. Counts that cannot be read are an error with Retry, never zero.
- **Activation change** (`POST /api/admin/categories/[reference]/activation {isActive, reason, expectedRev, idempotencyKey}`, `categories.activation` plus `categories.read`): main categories only; one snapshot transaction with the conditional overlay write (insert at revision 1 or update conditional on the revision seen), the audit row (unique `operationKey`, request hash) and the recovery event; same key + same request = original answer, same key + different request = 409, stale revision or no change = 409, two administrators at once = one wins. It writes only the main category's flag: no product, inquiry, quotation, snapshot or child flag is touched; reactivation restores only the central rule (nothing is approved, reopened or replayed). After the commit the overlay, snapshot and directory refresh in the process; a failure leaves the event for the worker sweep (`sweepCategoryEvents`); other instances converge within the snapshot TTL (60 s) and new publications, inquiries and lead commits re-read the database, so they never wait for that.

## Not implemented, and exactly why
| Operation | Blocker |
|---|---|
| Create category | A database-created node would not exist for the public routes, the product references, the supplier selectors, the attribute definitions or the matching policy: all read the code-defined taxonomy. Needs the taxonomy migrated into a database model first. |
| Rename / re-describe | The same consumers read the code constants, so an edit would show only in the admin page. |
| Change parent / change slug | URLs, saved links, product category ids and approved snapshots depend on the identity and path; there is no redirect layer, and a cycle/depth guard is moot until nodes can move. |
| Activation below a main category | Departments and product categories are keyed by catalogue names in the listing engine, so a separate flag cannot be enforced everywhere. "Reactivating a parent does not reactivate independently disabled children" is therefore trivially true today (there are none). |
**Migration path (not run, nothing in production changed):** move the code-defined nodes into a `categories` collection with their current ids and slugs preserved (idempotent, dry-run first, reporting inserted / updated / rejected / conflicting nodes and slug collisions), make `getCategoryDirectory` read it behind the same overlay precedence, add an alias/redirect collection for slugs, then enable create, edit, parent and slug operations behind the existing capability model. Rollback = point the directory back at the code constants (the overlay keeps working).

## Capabilities (default deny)
`categories.read`, `categories.activation`, `categories.audit` (activity and the internal reason). No create / edit / parent / slug capability exists because those operations do not. Scope = capability (the admin model has no organisation or category scope).

## Documented residuals
- At a cold start with the database unreachable the overlay cannot be read: the platform serves the code-defined categories as active until the database returns (authorization-grade writes also need the database, so they fail meanwhile).
- Catalogue (CSV) products carry no category activation of their own beyond their main category (all apparel); inactive-category products stay reachable to their owners and admins as before (nothing is deleted or hidden from owners).
- Product moderation of a pending submission is refused for an inactive category by the existing approval check (`getManagementCategories`).
