## Implementation map (audit result)
- **Managed unit:** the supplier COMPANY (`supplier_companies`: `_id`, `ownerUserId`, `sellerKeys`, `status` ACTIVE | SUSPENDED, `verificationStatus` always UNVERIFIED). Its profile (name, city) lives on the owner's `users.supplier` and the company profile; there is no separate membership model (the owner is the only member). No duplicate admin storage and no `/admin/companies` module were created. The reference is the company `_id` (24 hex); the short code `CMP-` + last 8 characters is display only.
- **Existing enforcement found:** `status: "ACTIVE"` was already required by the public product loader (`approvedProducts.ts`), the worker's candidate freeze and recipient commit, `findCompanyBySupplierKey`, product seller-key linking (`sellerMapping.ts`) and every supplier page/API guard. **Gaps found and closed:** `isProductPublicNow` (used before new inquiries) ignored the company; a direct inquiry to a suspended company's key or linked catalogue seller was accepted; the worker's company check was a read (write-skew against a concurrent suspension); product approval ignored the company.
- **Reused:** `AdminShell`, `requireAdminPage/Api`, the Page 57 drawer/tab/dialog styles and components pattern, `adminAuditLog` (now `src/lib/admin/auditLog.ts`), `rateLimit`, `isCrossSiteWrite`, `readSmallJson`, `csvCell`, `notifySupplier`, `invalidateApproved`, the worker sweep, the `it-guard` pattern, `/admin/company-links` and `/admin/products` as destinations.

## Identities kept apart
User account · company · membership (none) · catalogue seller identities (`sellerKeys`, admin-linked only, plus the company's implicit `co:<id>`) · verification (no workflow; **Page 53**; shown only as "Unverified") · public product eligibility (the product's own review/unpublish state AND the company being ACTIVE). A company with no linked catalogue seller is normal and is never labelled inactive or invalid. Counts are of companies.

## Capabilities (default deny, from the account record on every request)
`suppliers.read` (page, list, counts, detail) · `suppliers.links` (seller links) · `suppliers.contacts` (owner name, e-mail, phone) · `suppliers.suspend` · `suppliers.reactivate` · `suppliers.audit` (activity and the internal suspension reason) · `suppliers.export`. Every route also needs `suppliers.read`. Related links need the destination's own capability (`sellers.map` for Company Links, `products.read` for the product list and counts, `products.review` for Product Review); each destination re-authorizes. **Scope = capability only:** the admin model has no organisation or category scope, so none is implied. Grants are made by an operator in the database (`ADMIN_ACCESS.md`).

## Operational policy (what suspension does)
SUSPENDED company: excluded from public discovery (its products and supplier page, through the public loader, refreshed after the commit); refused as the target of NEW direct inquiries (its own key, and a catalogue seller linked to it); receives no new matched-lead recipient (the commit-time check); product approval for it is refused until reactivation; **its supplier workspace is closed** — every supplier page and API except Help & Support and Account Security refuses it (as before this page); existing history stays stored; no session is revoked, no account is suspended or deleted, the owner's other roles are unaffected.
**Documented policy conflicts:** (1) the existing guards already close the whole supplier portal to a suspended company, including read-only history. That is stricter than "read-only history for authorized staff"; it was **kept** (a stronger restriction is not silently loosened) and support and account security were opened (`allowSuspended`, `requireSupportApi`), which the requested policy asks for. A read-only history view for suspended companies is not built. (2) Legacy catalogue seller listings (CSV) linked to a suspended company stay publicly browsable, because the legacy catalogue has no company state to filter; new direct inquiries to those sellers are refused and no lead is routed. (3) A suspended company's owner cannot open the supplier notification list (the supplier API refuses it): the supplier layout shows a restriction banner and Support stays open.
Reactivation restores company access and eligibility only. It does **not** verify the company, approve pending products, clear a product's own unpublish restriction, reopen closed requirements, restore expired quotations, transfer seller ownership or replay past leads. Products approved and not individually unpublished become public again through the one effective-eligibility rule. The detail shows product counts (published, awaiting review, individually unpublished) so the effective state is visible.

## Status change flow
`POST /api/admin/suppliers/[reference]/suspend {reason, noticeCode, expectedRev, idempotencyKey}` and `/reactivate {reason, expectedRev, idempotencyKey}`. Reason 10–500 characters (internal, never shown to the supplier); the supplier-visible text is one of three fixed notices (`NOTICE_CODES`), never free text. **One snapshot transaction:** conditional update (`status` and `statusRev`), `admin_audit_log` row (trusted actor, company, reason, before/after, `operationKey`, request hash, server time) and the `company_status_events` recovery row (unique per company + revision). Same key + same request = original answer (`replay: true`); same key + different request = 409; stale revision or wrong state = 409; unknown or malformed id = 404; missing audit persistence = the transaction aborts (503, nothing changed). After the commit: the public snapshot is refreshed and one in-app notice is recorded from the stored event; either failing leaves the event pending and the worker sweep (`runDistribution` → `sweepStatusEvents`) retries it; the change is never repeated. Notices are in-app only (no e-mail or SMS).
**Concurrency guarantee:** the lead commit (`addRecipientIn`) and the submit transaction (`guardCompanyWrite`) check the company with a WRITE to the company document; a suspension is a write to the same document, so a commit that saw the company ACTIVE before the suspension committed conflicts, retries and then skips or refuses. A queued lead notice for a company that is no longer ACTIVE is not recorded (`deliverNotice` resolves the owner only for an ACTIVE company). Residual: guest and sample-listing inquiries (no transaction) rely on the early check only.

## API, data and indexes
`GET /api/admin/suppliers` (q, status, mapping, city, sort, page, `facets=1`; unknown values 422; default 20, max 50; company counts in the same response, so no separate summary route) · `GET …/[reference]` · `GET …/[reference]/activity?cursor=` · `POST …/suspend` · `POST …/reactivate` · `POST /api/admin/suppliers/export` (≤ 5,000 rows, same filters, no contact data, formula-safe, audited `SUPPLIERS_EXPORTED`). Statuses 401, 403, 404, 409, 413, 422, 429, 503 safe; `private, no-store`.
New optional fields on `supplier_companies` (no migration, absent = 0): `statusRev`, `suspension{at,by,reason,noticeCode,revision}`, `guardAt` (the worker/submit write). New collection `company_status_events` (unique `dedupeKey`, pending index). New indexes (lazy, idempotent): `admin_suppliers_updated`, `admin_suppliers_status`, `admin_suppliers_created`, `audit_company_newest` (partial). No uniqueness migration was needed. Name and city search join the owner's `users` record after the indexed company-level filters; with only status/mapping filters and an updated/created sort the page is cut before the join. **`explain` was not run** and no latency was measured (no isolated database): name search and name sort scale with the company count.

## Sign-in return
Same mechanism as Page 57: anonymous visitors reach `/sign-in?next=<path + validated filters + open review>`; the server validates it again (`safeNext`) and resolves the landing path from the stored role.
