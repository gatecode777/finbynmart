## C. Strict technology rules

- No Tailwind. No Bootstrap. No second CSS framework.
- No UI component libraries, no icon libraries other than Lucide React, no new dependencies without a stated need. (`framer-motion` is installed but unused; do not start using it casually.)
- Lucide React only for icons. Lucide has no brand icons, so the footer social links use hand-drawn outline glyphs in `src/components/layout/Footer/SocialIcon.tsx` (added at the owner's request). No emoji.
- CSS Modules for component styles; global tokens and resets only in `src/styles/`.
- `next/image` for images. Server Components by default; Client Components only for interaction, state or browser APIs.
- Reuse shared components. Follow existing conventions (folder per component, `index.ts` re-export, `Component.module.css`).
- TypeScript strict; no suppressed errors.
- **No fake data presented as real, no fake success.** Sample content is allowed for visual development but must be flagged in a code comment and listed in `docs/MISSING_ASSETS.md`. Never invent backend endpoints. The requirement and inquiry forms intentionally show an honest "not connected" message until a real backend exists (`src/lib/api/*`).

## F. Functional requirements

Every interactive element must work: buttons act, search submits and returns relevant results, filters filter, forms validate and submit (or honestly report they are not connected), pagination changes data, dropdowns/modals open and close, links navigate, save/wishlist persist, authentication protects restricted pages. No decorative buttons. No fake success notifications.

## G. Responsive requirements

Every page must work at 320, 344, 375, 390, 414, 480, 576, 768, 820, 1024, 1280, 1366, 1440, 1600, 1920 and 2560px, in portrait and landscape, and at browser zoom 80/90/100/110/125/150/200%. No horizontal overflow, clipped text, overlap, broken grids, squeezed cards, inaccessible mobile controls or fixed-width layouts. Tables need a responsive strategy. Mobile is designed, not a shrunken desktop. Use Grid/Flexbox/`clamp()`/`minmax()`; grid tracks holding inputs or text use `minmax(0, 1fr)`.

Test with the scripts in `docs/responsive/tools/` (need `npm i puppeteer-core` and a running `next start`). Report only what was actually run, and state that Firefox, Safari and real devices are untested unless they were.

## H. Accessibility

Semantic HTML, keyboard navigation, visible focus, accessible labels, contrast of at least 4.5:1, meaningful alt text, accessible dialogs and menus (focus trap, Escape, focus return, `inert` when closed), reduced-motion support.

## I. Performance

`next/image` with correct `sizes`; lazy-load below the fold; avoid unnecessary client components and JavaScript; prevent layout shift; efficient data fetching; **never load the whole 21,392-product catalog per request when a count or small query will do**; add `loading.tsx`/`error.tsx` boundaries for pages with async data. Targets once measurable: Lighthouse 90/95/95/95, LCP ≤ 2.5s, INP ≤ 200ms, CLS ≤ 0.1.

## J. Security

Protect dashboard routes; enforce authorization on the server and never trust client-side role checks alone; validate all input on the server; prevent access to other users' records; rate-limit auth and form endpoints; never expose or commit secrets (`.env.local` is git-ignored; never print credentials); protect buyer and supplier data. Known open items are in `docs/audit/11_SECURITY_AUDIT.md` (no rate limiting, no role enforcement yet, no security headers).

## L. Multi-portal architecture (permanent: applies to every new page and module)

Finbyn Mart is one marketplace with separate role-based portals. Page numbers are tracker identifiers, never routes; a page is classified by its route.

- **Portals and routes:** PUBLIC (`/`, the marketplace site including sign-in and registration), BUYER (`/buyer/*`, dashboard `/buyer/dashboard`; the owner's Pages 1–38 buyer work), SUPPLIER (`/supplier/*`, dashboard `/supplier/dashboard`; Page 39 onward; **built in part**: dashboard, quotations (list, create, details, versions), inquiry details and responses, orders; the other supplier pages are not built), ADMIN (`/admin/*`, `/super-admin/*`; own RBAC; **not built yet**). Never classify a supplier page as buyer or the reverse. The tracker has a Portal column for every page.
- **Navigation:** each portal has its own sidebar, topbar and navigation holding only its modules. Buyer: Dashboard, Product Explorer, My Inquiries, Quotations, Orders, Saved Products, Saved Suppliers, Compare Products, Profile & Company, Address Book, Settings & Notifications, Account Security, Help & Support (`src/components/buyer/buyerNav.ts`). Supplier: Dashboard, Inquiries & Leads, Quotations, Orders, My Products, Inventory, Analytics & Reports, Company Profile, Settings, Help & Support. Never show supplier or admin links to a buyer or the reverse; never reuse a whole dashboard shell across roles (logo, buttons, inputs, toasts, modals, icons, tokens and responsive utilities may be shared). Both portals use the one Finbyn Mart identity (teal and gold, Anton + Montserrat, Lucide only, no Tailwind or Bootstrap).
- **After sign-in:** the SERVER resolves the account's stored role and status and returns the landing path (`resolvePostLoginPath` in `src/lib/auth/portals.ts`): buyer → `/buyer/dashboard`, supplier → `/supplier/dashboard`, admin → the existing authorized admin route. A requested `next` page is kept only if it is public or in the user's own portal. Never send every user to one common dashboard; never read the role from the request body, a cookie or browser storage. While `SUPPLIER_PORTAL_AVAILABLE` is false a supplier lands on the public home page (not a 404); flip it in the change that builds the supplier dashboard.
- **Roles:** an account has ONE role, set at registration; there is no multiple-role or active-role selection yet. If it is ever added, the active role must be an explicitly authorized server-side choice, validated on every request.
- **Route protection:** every portal route and API checks the verified session and role on the server (`requireBuyerPage/Api` for the buyer portal; supplier and admin equivalents must be built with their portals, with company membership for suppliers). Hidden navigation is never protection. An unauthorized visitor is redirected to sign-in or refused (403 for APIs); no private data is rendered before authorization. Enforce isolation again inside services and repositories.
- **Data isolation:** never trust `buyerId`, `supplierId`, `companyId` or a role from the client. A supplier API resolves the authenticated supplier's company membership; a buyer API resolves the authenticated buyer. A supplier must never reach another supplier's leads, quotations, orders or private company data, nor a buyer another buyer's records.
- **One marketplace:** both portals read the same central sources for products, categories, suppliers/companies, inquiries, quotations and orders; never build a second catalogue per portal. Role-specific APIs and DTOs expose only what the role may see.
- **Testing before a portal is called complete:** role redirects after sign-in, cross-portal route and API refusal, company tenant isolation, direct URL access, session expiry, logout, multiple-role behaviour, and responsive navigation. `docs/page-reports/tools/portal-routing-test.mjs` and `portal-rules-unit-test.mjs` cover what exists today; extend them with each portal.

## Standing instructions from the owner

1. **Build the backend together with the pages.** When a page prompt (PRD) says data must be saved, authenticated or protected (requirements, inquiries and quotes, wishlist, accounts, dashboards), build that backend in the same piece of work: MongoDB collections with indexes, API route handlers under `src/app/api/`, server-side validation and authorization, rate limiting, and the UI wired to it. Do not leave a form that only validates. Never show a success message that the backend did not produce. Do the backend after the page it serves is complete, in page order (Pages 01–04 first). Test against a throwaway database (`MONGODB_DB=<name>_test`), never the live collections, and drop it afterwards.
2. **If a page already exists, modify it; do not rebuild it.** When a page (or its components) is already in the repo, change it only as far as needed to match the new UI reference and PRD: keep the working data flow, routes, tests and shared components, and reuse or extend them. Rebuilding from scratch needs an explicit reason written in the page report.
3. **One shared view per page family.** Pages that differ only in data (category and subcategory pages) must use the same component (`CategoryListingPage`), not copies.
4. **No loading boundary above a page that can 404 or redirect.** A `loading.tsx` makes Next stream a 200 before `notFound()`/`redirect()` runs (a soft 404). Only add one where the page cannot return those.
5. **Form feedback.** Every form shows validation and server errors inline, under the field they belong to (`aria-invalid` + `aria-describedby`, plus a focusable error summary), and reports the outcome of every submit or save with the shared toast (`flashToast` from `@/components/ui/Toast`): success only after the server acknowledged it, an error toast when it was not saved or not submitted. Never a toast alone for a field error, never a success toast for something the backend did not do.
6. **Images use ImageKit** (`IMAGEKIT_PUBLIC_KEY`, `IMAGEKIT_PRIVATE_KEY`, `IMAGEKIT_URL_ENDPOINT` in git-ignored `.env.local`; placeholders in `.env.example`). Uploads go through our server (`src/lib/media/imagekit.ts`, REST, no SDK): size and magic-byte checks first, private key never sent to the browser, only URLs under our endpoint are stored, removing an image from a product only unlinks it (the ImageKit file is not deleted).

## Quotation rules (permanent; every quotation feature, supplier or buyer)

- **One quotation system.** The `quotations` collection and `src/lib/quotations/` (`quotationRules.ts` lifecycle, `money.ts`, `service.ts`) are the only quotation model. The supplier side is `src/lib/supplier/quotationRules.ts` + `quotationService.ts` and `/api/supplier/quotations/*`; reuse them, never add a second quotation collection, status set or price calculation.
- **Money is server-calculated and exact.** Amounts are integer minor units, arithmetic is BigInt (`priceBreakdown`/`totals`), percentages are basis points rounded half up, no floating point, no client-supplied subtotal/tax/total is ever trusted, no tax is assumed (a quotation without a stated tax shows "before tax"). Keep currency and unit with every amount; never add, compare or rank different currencies (that is why there is no amount sort until a `totalMinor` is stored by the creator).
- **Versions are immutable.** One document per version, one `isCurrent`; a sent version is never edited, a revision is a new version and the older becomes `SUPERSEDED`; an accepted snapshot never changes. List and count only `isCurrent` (one logical quotation = one lineage). Prices come from the saved version, never from the catalogue.
- **Who writes which status.** Acceptance, rejection and revision requests come only from the Buyer Portal routes; a supplier can only withdraw (current version, waiting on the buyer, still valid, one atomic conditional update, nothing deleted). Expiry is derived from `validUntil` at read time, never stored or decided by the browser. Never infer a decision from time or a message; never show Viewed / Under review without tracking.
- **Supplier isolation.** Every supplier quotation query and update carries `supplierKey ∈ company.sellerKeys` from the verified session; unknown, malformed and foreign references give the identical 404; the related inquiry is read only if it is also addressed to an owned seller; buyers are shown by business name only (no email, phone, address or private message), also in exports.
- **Listings and exports are bounded and indexed**: limit ≤ 50, page ≤ 1000, export ≤ 5,000 rows built in the response with `csvCell` (formula-safe) and logged by counts; counts come from one covered aggregation; no N+1; private/no-store.
- **Never fake** a PDF, an order, a supplier notification, an email or a creation workflow: PDF, order conversion and supplier notifications are BLOCKED until real modules exist (`docs/backend/PAGE_42_QUOTATION_PDF_RULES.md`, `PAGE_42_ORDER_CONVERSION_RULES.md`). When a buyer notice is created (withdrawal), say whether it was really recorded; never claim an email. Order creation from an accepted quotation, when built, must be once per quotation (unique `quotationReference`) and carry the stored amounts.
- **Create / revise / withdraw (Pages 43, 44).** A draft is a `quotations` document with status DRAFT (never visible to a buyer); a **revision is a new version of the same reference**, a DRAFT with `isCurrent:false` that is copied from the current version's own submitted inputs, and the buyer keeps seeing the current offer until it is submitted, when the previous current version becomes SUPERSEDED **in the same transaction** (it fails with 409 `BASE_CHANGED` if the buyer decided first). Only the current version, only while SENT / REVISION_REQUESTED, can be revised; accepted versions are immutable and no amendment exists. The server recalculates every amount (`computeQuote`); tax comes only from the configured `QUOTATION_TAX_RULES` (no default: submission is BLOCKED while unconfigured, drafts work); a submitted version is shown from its own snapshot, never recalculated from today's catalogue or tax settings. Drafts save with a required `expectedRevision` (409 on a stale one). Compare reads exactly two versions of one quotation, matches lines by stable id, and never computes a difference across currencies. PDF, quotation attachments and order conversion stay BLOCKED until real modules exist.
- **Inquiry responses (Page 41).** `inquiry_messages` is the ONE conversation store (type RESPONSE or CLARIFICATION, plain text, 10–2,000 characters, written only by the server with author / company / recipient / time from the session and the inquiry record, never edited or deleted); a message moves the inquiry only through steps the shared lifecycle allows (`statusPlan`) and never closes, quotes, accepts, orders or pays; lists are cursor-paged on `(createdAt, _id)`; the buyer's page reads the same rows. No read tracking, delivery or read receipt, buyer reply or attachment exists: never show one.
- **Mutations that must be exactly-once** (submit, revise, withdraw, respond): validate on the server; submit, revise and respond use `idempotency_keys` (unique company + user + operation + key, same key + same body = the original result, changed body = 409) and withdraw uses its atomic conditional update (`expectedVersion`) plus the unique outbox key (a second withdrawal is a 409); write the action, its status steps, the **`notification_outbox` row** and the idempotency record in ONE transaction (`session.withTransaction`, snapshot read, majority write; no partial-commit fallback), then deliver the buyer notice after the commit (`deliverOutbox`; a failed delivery never repeats or undoes the action and is retried when the supplier next opens a list or inquiry page; there is no scheduler and no e-mail, so never claim either). Report the notice honestly (`recorded` / `pending` / `not-recorded` when the buyer switched it off).
- **Rate limiting.** WRITES use `rateLimit()` (one exact database write per attempt); `rateLimitReserved()` is only for reads (it reserves blocks and over-counts under concurrency). Supplier write routes: respond 30 / 10 min, submit / revise / withdraw 20 / 10 min, save 120 / 10 min, export 10 / 10 min.

## Supplier orders rules (permanent; Page 45, tracker ID 112)

- **One order system.** The `orders` collection and the 13-status lifecycle in `src/lib/orders/orderRules.ts` are the only order model; the supplier side is `src/lib/supplier/orderRules.ts` + `orderService.ts` and `/api/supplier/orders/*` (list, summary, detail, export). Never a second order store, per-portal copy or status set. An order has exactly ONE buyer and ONE supplier (`supplierKey`): there is no multi-supplier order or sub-order, so counts are orders, and a supplier DTO shows only the order of its own company (`supplierKey ∈ company.sellerKeys` from the session; identical 404 for unknown, malformed and foreign references).
- **Nothing creates an order yet** (no checkout, order-confirmation workflow or quotation conversion): never infer an order from an accepted quotation, never show a sample order, never offer Create, Confirm, Cancel, Update Fulfilment or Mark Paid until an approved workflow exists (the page is read-only and its capabilities say why). Payment has no source: it is always "Payment status unavailable", never derived from acceptance, confirmation, dispatch or delivery; lifecycle (stored status), fulfilment (its delivery meaning) and payment stay three different facts.
- **Status groups** (`ORDER_GROUPS`) partition the 13 stored statuses (chip counts add up to All; Ready to Dispatch is not inside In Progress); `status` is ONE canonical filter (a group key or an exact status) shared by chips, cards and the select; counts are taken in one database-side grouped read under the search / date / currency filters (not the status); no amount is ever summed or ranked across currencies; amount sorts need one currency; dates have an explicit basis (order date / last updated). Docs: `docs/backend/PAGE_45_ORDER_STATUS_MODEL.md`.
- **Search / export.** Search = order, quotation and inquiry reference prefixes and a product-name substring inside the company's own orders, matched literally (escaped); buyer names are not searchable (an order stores only the buyer id). Export = the Page 42 pattern (permission `exportOrders`, exact rate limiter 10 / 10 min, cross-site refusal, ≤ 5,000 rows built in the response, `csvCell`, logged as `supplier_orders_exported` by counts and filter names, no stored file, no background job). Indexes: `supplier_orders_newest`, `_status`, `_updated`, `_amount` (plus the dashboard's `supplier_orders_placed`, a prefix of the first).
- Docs: `docs/backend/PAGE_45_*.md`, `docs/page-designs/45-supplier-orders.md`, `docs/page-reports/45-supplier-orders-report.md`; tests: `docs/page-reports/tools/45-supplier-order-rules-unit-test.mjs` (run with `--import ./docs/page-reports/tools/alias-register.mjs`) and `45-supplier-orders-test.mjs` (one server on :3100; `SKIP_PERF=1` skips the 10,000-order group).

## API performance rules (permanent)

- Measure before and after with `docs/performance/tools/bench.mjs` on a production build with nothing else running; never claim an improvement without both numbers, and report what did not improve. Reports live in `docs/performance/`.
- Targets (p95): simple read < 300 ms, detail < 350, paginated listing < 400, filtered or search < 500, write < 500, aggregation < 800. State plainly where a route misses them (see `docs/performance/API_OPTIMIZATION_SUMMARY.md`).
- Every list endpoint is paginated with a maximum page size (50); never return an unbounded list. Return only the fields the UI needs (allow-listed DTOs), never whole documents.
- Every MongoDB query must use an index (`explain` shows no COLLSCAN or blocking sort); add the index with the feature. Reuse the one shared client (`src/lib/db/mongo.ts`).
- Cache only public, read-only data, with a short TTL, single-flight loading and an explicit invalidation path; never cache personal data. `FINBYN_PUBLIC_CACHE_MS=0` switches caches off (the functional test server uses it).
- Do not load the whole catalogue per request; use the listing engine's index and its result cache.
- Do not run load tests against production or live collections; use the throwaway database.
